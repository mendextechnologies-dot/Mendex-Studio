1. Decision and scope
Version 1.3 is reported implemented by the project owner. Version 1.4 extends the existing Studio, not a replacement or rewrite. Codex must first inspect the repository and verify actual implementation status, tests and architecture before making changes. No product-specific development is authorized.
Existing reference: Mendex Engineering & Validation Platform Master Guide v1.3 and Mendex Studio Detailed Software Architecture/UI-UX Implementation Specification v1.0. Preserve the Windows-first, local-first, offline-capable, modular Python/PySide6 approach unless repository evidence or explicit approval requires a change.
2. Outcomes and non-goals
A reliable tool registry showing availability, version, license constraints, readiness and supported capabilities.
A reusable adapter framework with safe local execution, timeouts, cancellation, logging and diagnostics.
Common project artifact and evidence metadata, simulation-job records and reproducible report scaffolding.
A functional workflow using supported tools and synthetic/demo inputs, without asserting engineering validity.
No specific product design, certification, manufacturing release, mandatory cloud service, or unapproved paid-license purchase.

4. Implementation phases and acceptance gates
Phase 0 — Baseline audit
Work: Inspect repository, compare v1.3 commitments to code, run existing tests, record gaps and freeze a regression checklist.
Exit gate: Signed baseline matrix; no regressions; docs/IMPLEMENTATION_STATUS.md updated.
Phase 1 — Tool registry and discovery
Work: Create catalog entries for all 18, tool/resource types, OS and license notes, detection, version probing, health checks and manual path configuration.
Exit gate: All 18 visible; statuses distinguish NOT_INSTALLED, DETECTED, READY, UNSUPPORTED, ERROR and UNKNOWN; no false READY.
Phase 2 — Adapter SDK and safe runner
Work: Define typed contracts for discovery, configuration, launch, job submission, progress, cancellation, results and diagnostics. Use subprocess isolation and controlled working directories.
Exit gate: Mock adapter passes contract tests; failures/timeouts/cancellation handled; no untrusted arbitrary code loading.
Phase 3 — Core connectors
Work: Implement and verify practical local integrations for KiCad, LTspice, FEMM, FreeCAD and Python, with Git support. Scope each by actual installed version and CLI/script capability.
Exit gate: Per-tool smoke tests with synthetic inputs, logs, artifact manifests, explicit limits and version evidence.
Phase 4 — Extended connectors and data
Work: Evaluate Qucs-S, OpenModelica, Jupyter and MagNet/SwitchLossDB dataset workflows; import provenance and licensing metadata.
Exit gate: At least one verified extended connector and one dataset import workflow; unsupported operations clearly marked.
Phase 5 — Workflow and evidence UI
Work: Build job queue, status, logs, result browser, artifact provenance, parameter metadata and exportable framework reports.
Exit gate: Demo job can be started, monitored, cancelled/retried and reopened; reports cite actual evidence.
Phase 6 — Optional commercial connectors
Work: Design configuration-only or licensed adapters for PLECS, MATLAB/Simulink, Ansys Maxwell/Icepak and SolidWorks.
Exit gate: No mandatory paid dependency; adapters report unavailable or unverified until licensed and tested.
Phase 7 — Acceptance and handover
Work: Run regression suite, security/path tests, documentation review and user walkthrough; maintain backlog.
Exit gate: Owner accepts demonstrated functions and known limitations; no engineering certification implied.
5. Technical contracts
ToolDescriptor: id, name, kind (application/dataset/benchmark), supported OS, version, license status, capability declarations and source URL.
ToolAdapter: detect(), verify(), capabilities(), configure(), launch() and optional submit_job(), cancel_job(), collect_results().
JobRecord: job ID, workspace ID, tool/version, input hashes, parameters, timestamps, status, logs, output artifacts and failure reason.
ArtifactManifest: relative path, file type, SHA-256, source job, provenance, creation time and review state.
Security: explicit executable allowlist, path validation, no silent downloads, no arbitrary shell strings, safe process isolation and bounded resources.
Status semantics: installed is not validated; a successful software self-test is not an engineering pass.
6. UI and developer experience
Add Tools & Integrations dashboard, tool detail/configuration screens, Jobs & Results view, evidence browser, and troubleshooting panel. Retain existing navigation, workspace lifecycle and VS Code/Codex integration. Show actionable diagnostics and avoid dead buttons. AI suggestions must remain reviewable, separate from verified simulation evidence, and provider-neutral.
7. Codex implementation instruction
Read existing v1.3 code and documentation first; do not assume this document reflects actual implementation.
Produce a gap matrix and propose minimal incremental changes; preserve existing working functionality.
Implement one phase at a time with tests and evidence; record decisions and dependency/license rationale.

9. Two-agent parallel delivery model (v1.5 addendum)
Status: Execution assignment. v1.3 is treated as implemented per project-owner confirmation; both agents must verify actual repository state before changing code. This addendum supersedes single-agent instructions in section 7 where responsibilities conflict.
Agent naming: Agent 1 = Codex (VS Code). Agent 2 = Agentforce / Antigravity (the second coding agent selected by the project owner). Agent 2 is a role label, not a requirement to use Salesforce Agentforce.
9.1 Non-negotiable boundaries
No specific engineering product design or product-specific simulation models. Build a reusable Studio only.
No rebuilding of working v1.3 functionality; audit, preserve, extend and regression-test.
Two independent Git worktrees/branches; never have both agents write to the same worktree.
No simultaneous edits to shared files. Codex owns contracts, schemas, UI, DB migrations and integration merges.
No claims that a tool works until installed-version checks and repeatable smoke tests demonstrate it.
Commercial tools are optional, license-gated adapters; do not bundle proprietary executables, models or datasets.
No automatic safety certification or equivalence claims between simulation and physical behavior.

9.4 Contract freeze — prerequisite for parallel coding
Codex publishes ToolDescriptor: stable ID, name, category, version, OS, license, capabilities, configuration schema.
Codex publishes ToolAdapter interface: detect(), verify(), supported_operations(), execute(request, context) and optional launch().
Codex publishes JobRequest: schema_version, job_id, workspace_id, tool_id, operation, input paths, parameters, timeout, provenance.
Codex publishes JobResult: status, timestamps, exit code, structured diagnostics, outputs, evidence paths and tool/version.
Codex publishes EvidenceManifest: file hashes, source labels, run metadata, unit conventions, raw-vs-derived distinction and review status.
Agree error codes and status transitions: NOT_CONFIGURED, NOT_INSTALLED, DETECTED, READY, UNSUPPORTED, ERROR; QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED, TIMED_OUT.
Contract tests and JSON fixtures must pass for a fake adapter before Agent 2 begins implementing real adapters.
9.5 Parallel sprint schedule and gates
Gate A — Day 0: Audit and freeze
Codex: map existing v1.3 modules and tests, establish branches/worktrees, publish contracts and fake adapter.
Agent 2: audit tool availability, OS/license constraints and proposed adapter strategy; no shared-code changes.
Exit: contract tests pass; owners and directories documented.
Sprint 1 — Registry + execution foundation
Codex: Tool Center and settings, registry persistence, job/evidence schemas and fake-adapter UI.
Agent 2: safe runner and executable detection/verification framework with fixture tests.
Exit: UI can execute fake job; runner handles success, failure, timeout, cancellation.
Sprint 2 — Core tool integrations
Codex: job list/details, progress, log viewer, tool configuration and report skeleton.
Agent 2: LTspice, KiCad, FEMM and FreeCAD adapters, each gated by local support and licensing.
Exit: each claimed supported operation has reproducible smoke evidence; unavailable tools clearly labeled.
Sprint 3 — Extended tools + research
Codex: dataset catalog, import UI, provenance, report exports and error recovery.
Agent 2: Qucs-S, OpenModelica, Python, Jupyter, Git; SwitchLossDB and MagNet data/benchmarks with source/license checks.
Exit: import and run traces recorded; research assets distinguished from executable simulators.
Sprint 4 — Optional tools + acceptance
Codex: optional-tool UI, final regression suite, docs, packaging only if approved.
Agent 2: non-invasive discovery/stubs for PLECS, MATLAB/Simulink, Ansys Maxwell/Icepak and SolidWorks; no forced installation.
Exit: end-to-end demonstration, evidence, known limitations and owner sign-off.
9.6 Daily coordination and merge protocol
Every work session: each agent posts Completed / In progress / Blocked / Changed files / Tests / Next handoff.
Agent 2 raises a PR with adapter source, contract-test results, compatibility matrix, raw logs and sample output manifests.
Codex runs contract tests first, then UI/integration/regression tests; resolves conflicts only in Codex-owned integration branch.
If contract must change, pause affected Agent 2 adapter work; Codex versions the schema, updates fixtures and notifies Agent 2.
No agent merges its own unreviewed cross-boundary changes; no force-push to shared branches.
Mark an integration READY only for a tested version and specific operation, not merely because an executable was found.
