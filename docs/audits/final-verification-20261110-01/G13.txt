1. Executive scope
MEVP is a repeatable engineering workflow rather than a bundle of software. It records product requirements, generates models, invokes approved simulators, preserves raw outputs, validates evidence, and supports controlled design release. A single Python core is shared by the desktop application, CLI and VS Code integrations.
1.1 In scope
Transformer and magnetic-component calculations; 2D magnetic analysis and optional advanced 3D workflows.
Electrical simulation, PCB design checks, mechanical modeling, thermal studies and parameter optimization.
Local desktop experience, one-command developer onboarding, team collaboration and reproducible reports.
AI-assisted development using Codex, with explicit human review and tool execution boundaries.
1.2 Out of scope for v1
Automatic safety certification, guaranteed simulation-to-hardware equivalence, unattended high-voltage tests.
Full bidirectional lossless conversion among LTspice, FEMM, KiCad and FreeCAD.
Cloud multi-tenant platform or proprietary EDA replacement.

8. VS Code and Codex workflow
Repository AGENTS.md is the AI instruction entry point; link to versioned engineering policies and do not paste an enormous manual into it. Treat Codex output as proposed changes subject to tests and review. Codex can create models/scripts and run approved local simulations, but cannot sign releases or erase raw evidence.
# AGENTS.md (starter)
Read docs/architecture.md and docs/engineering-rules.md before changes.
Use SI units internally and typed, versioned schemas.
Never fabricate simulation or hardware measurements.
Never modify immutable evidence or approved release baselines.
Record tool version, inputs, model hashes, logs and solver exit codes.
Mark unavailable checks NOT_EVALUATED, never PASS.
Run unit, integration and reference tests before proposing a merge.
Require human approval for hazardous tests, hardware control and releases.
Recommended VS Code tasks: Mendex: Doctor; New Project; Run FEMM; Run LTspice; KiCad ERC/DRC; Validate; Generate Report; Open Studio. Implement these as tasks invoking MEVP CLI; optionally add a VS Code extension later. AI requests should specify project ID, approved topology, acceptance criteria and allowed tools.

10. Adapter plugin contract and extension policy
class ToolAdapter(Protocol):
    def probe(self) -> ToolCapabilities: ...
    def validate(self, spec: DesignSpec) -> ValidationResult: ...
    def prepare(self, spec: DesignSpec, workdir: Path) -> PreparedJob: ...
    def run(self, job: PreparedJob, timeout_s: int) -> RunRecord: ...
    def parse(self, record: RunRecord) -> ResultBundle: ...
    def self_test(self) -> TestReport: ...
Each adapter must declare tool ID, semantic adapter version, supported tool-version ranges, supported OS, features, input/output schemas, timeouts, error taxonomy and benchmark fixtures. Never allow plugins to mark their own engineering results approved.
10.1 Adding a new tool
Create proposal: use case, alternatives, official license, platform support, maintenance status and security risks.
Implement adapter from template and registry manifest; pin dependencies.
Add unit tests, simulated failure tests and an independently checked benchmark.
Verify output provenance, timeouts, cancellation, logging and isolation.
Expose only registered capabilities in Studio and CLI; add docs and install checks.
Release behind feature flag; qualify per OS and tool version before default enablement.
11. Engineering workflow: transformer pilot
Pilot MX-HVDC-001 is illustrative: 24 V nominal input, 1 kV / 50 mA output, 100 kHz candidate flyback topology. These values are not sufficient to specify a safe transformer. Collect input range, duty-cycle limits, control method, operating mode, isolation category, pollution degree, altitude, ambient temperature, winding construction, insulation system and target standards before design approval.
Requirements gate: signed product specification and applicable standards profile.
Analytical gate: turns ratio, peak current, core flux swing, inductance, losses and margins with cited equations and material data.
FEMM gate: core geometry/material, excitation, boundary conditions, mesh convergence, saturation margin and leakage assumptions.
Electrical gate: LTspice switching waveforms, startup, line/load corners, stress and transient tests.
PCB gate: KiCad ERC/DRC, creepage/clearance review, footprint verification and assembly review.
Thermal gate: loss budget and justified thermal model; lab confirmation later.
Physical gate: approved high-voltage test plan, rated equipment, interlocks and authorized supervision.
Release gate: all mandatory evidence present, deviations approved, independent engineering review.
12. Validation policy and statuses
Status
Meaning
PASS
Executed check met approved numerical criteria with evidence
FAIL
Executed check violated criteria
NOT_EVALUATED
Check not executed or required evidence unavailable
BLOCKED
Dependency, environment or safety gate prevents execution
WAIVED
Documented exception approved by authorized reviewer; not a pass
Rules should be machine-readable, versioned and associated with product type and standards profile. Critical safety requirements cannot be waived solely by a developer. A passing KiCad DRC or FEMM model is not proof of electrical safety, EMI compliance, dielectric withstand or production readiness.
13. Evidence and reproducibility
For every run store a manifest containing input hash, source commit, adapter/tool versions, OS, solver options, timestamps, exit code, stdout/stderr, raw results, parsed metrics, plots and validation rule version. Raw outputs are write-once; reports link to evidence IDs. For reproducibility, preserve model files and external material/library versions. Never overwrite the previous successful run.
14. Security and collaboration
Private GitHub repository; least-privilege access, protected main branch and peer review. Automated CI/CD checks will be introduced in a later phase.
Separate development, reviewed baseline and released artifact states.
No credentials in Git; use OS credential store or approved secret manager.
Allowlisted executable paths; subprocess timeouts; sandbox untrusted model files where feasible.
Log who initiated simulations and approved exceptions; restrict release signing.
Treat third-party CAD libraries, SPICE models and AI-generated code as supply-chain inputs requiring review.
15. Local testing and manual desktop packaging (CI/CD deferred)
For v0.1, run linting, schema checks, unit tests, adapter mock tests and desktop smoke tests manually on developer machines. Record results in a local test log. Package the desktop application manually after the end-to-end pilot passes. Automated CI/CD workflows, deployment pipelines and release automation are explicitly out of scope until a later phase.
16. Reporting and sign-off
Reports include document control, requirements traceability, assumptions, tool inventory, model inputs, plots, validation table, failures, outstanding physical tests, limitations, reviewer names and release status. Use separate labels for CALCULATED, SIMULATED and MEASURED results. The report generator must refuse to issue a RELEASED status without authorized sign-off.
17. Standards selection
Maintain a standards applicability matrix by intended use, jurisdiction, voltage, insulation and product classification. Candidate families to review include IEC 60664, IEC 61558, IEC 61010, IEC 62368, IEC 61000 and IPC-2221/IPC-2152. These are examples, not universal requirements; purchase and consult the applicable editions and qualified safety engineers.

19. Operational runbooks
19.1 When installation fails
Capture doctor output, OS build, exact tool versions and executable paths.
Check permission, antivirus quarantine, path quoting and missing runtime dependencies.
Run the tool standalone before diagnosing its adapter.
Use supported-version matrix; never silently downgrade tool versions.
Escalate with sanitized logs and reproducible reference project.
19.2 When simulation fails
Preserve failed inputs, logs and solver exit code.
Classify failure as environment, invalid model, numerical convergence or unsupported capability.
Do not report partial numerical outputs as successful results.
Retry only with a documented parameter change and new run ID.
19.3 When a tool is upgraded
Install in staging; run reference benchmarks and compare tolerances.
Review file-format/API changes and adapter compatibility.
Approve registry version update via pull request.
Publish release notes and retain rollback path.

PART IV — THREE-DAY FOUNDATION BUILD (v1.2 ADDENDUM)
Release intent: Mendex Engineering Studio v0.1 is an integrated, extendable desktop framework—not a completed or certified power-electronics design system. Build the framework now; enhance engineering capabilities as real product work exposes requirements. This addendum supersedes any earlier v1.0/v1.1 timelines or feature claims that imply fully automated engineering validation in three days.
24. Scope and Definition of Done
Primary domains: high-frequency transformers and magnetics; isolated/non-isolated DC–DC converters; high-frequency power supplies; MOSFET, IGBT and BJT switching devices; PCB design. Exclude enterprise PLM, supplier procurement, advanced AI, automated lab control and manufacturing release from v0.1.

26. Three-Day Execution Plan
Day 0 — 60–90 minute prerequisite
Confirm OS (Windows recommended for FEMM/LTspice compatibility), Python and Git versions, available native engineering tools, repo access and packaging target. Create baseline repository, API contracts, example JSON, task board and two branches. Commit contracts before either agent begins.
Day 1 — foundation
Codex: package structure, SQLite migrations, product/revision models, typed schemas, project-folder creation and service tests. Antigravity: PySide6 app shell, dashboard, product list/editor and mock service integration. Joint checkpoint: product created, saved, reopened.
Day 2 — extensibility
Codex: adapter protocol, tool discovery, validation result schema, run records, report service and reference tests. Antigravity: transformer/DC–DC/device workspace shells, Tool Manager, knowledge center, validation and reports views. Joint checkpoint: tool status and sample validation persist.
Day 3 — integration and release
Codex: CLI diagnostics, smoke tests, report evidence checks, error handling. Antigravity: real service wiring, VS Code/project launch, installation notes and basic packaging. Joint checkpoint: new product → spec → workspace → tool check → recorded result → report; tag v0.1.0.
27. Shared Contracts (Freeze Before Parallel Work)
Use typed Python Pydantic models and JSON serialization. The desktop UI calls a documented Python application service interface in-process for v0.1; a future FastAPI layer may expose the same operations for web or team use. Do not build two independent databases or duplicate validation logic.
Product
product_id (UUID), code, name, category, description, owner, created_at, updated_at, active_revision_id.
Revision
revision_id, product_id, revision_label, lifecycle_status (draft/in_review/approved/archived), specification_json, created_at; approvals are informational until an approval workflow exists.
ToolStatus
tool_id, display_name, configured_path, installed_version, detected, executable, compatibility (supported/unsupported/unknown), checked_at, diagnostic.
SimulationRun
run_id, revision_id, tool_id, adapter_version, status (not_started/queued/running/succeeded/failed/not_supported), started_at, ended_at, input_hash, artifacts[], log_path.
ValidationResult
check_id, revision_id, status (pass/fail/not_evaluated/physical_verification_required), rule_version, measured_value, unit, evidence_uri, reviewer, timestamp, notes. A PASS requires actual evidence and evaluated rule.
Report
report_id, revision_id, generated_at, input_hash, report_path, included_check_ids, warnings.
Service operations: create_product, list_products, get_product, update_specification, create_revision, create_workspace, list_tools, check_tool, list_runs, record_validation, list_validation, generate_report, open_in_vscode. Errors use typed error codes and actionable messages; all file paths are normalized and validated.

29. Installation and New-Engineer Experience
Prerequisites: Windows 10/11 development baseline (confirm actual compatibility per application); Python, Git, VS Code. LTspice, FEMM and KiCad remain separately installed and may require user interaction.
Quick start: clone private repository; create .venv; install project in editable mode with development extras; run python -m mendex_core.doctor; launch python -m mendex_ui. Final command names must match implementation and be verified before publishing.
Tool Manager: detect binaries using explicit user-configured paths and known installation locations; report unknown versions as unknown, never silently supported. Offer official download guidance rather than unsafe automatic installation.
Packaging: first ship source-based developer setup; optionally package PySide6 using a supported packager after tests. Packaging does not redistribute third-party tools without license review.
Team test: second engineer clones repository on clean machine, completes setup, creates product, launches VS Code, records a result, exports report and logs any missing dependency.
30. Engineering UI Experience Principles
Learn from Altium 365 (design context/reviews), Autodesk Fusion (discipline navigation), OpenBOM (revisions/BOM), and Siemens Teamcenter (traceability). These are inspiration, not dependencies or UI designs to copy. Initial navigation: Dashboard → Products → Product Detail → Engineering Workspace (Transformer, DC–DC, Switching Devices, PCB) → Simulations → Validation → Reports → Tool Manager → Knowledge Center.
Each product detail page must show product code, current revision, lifecycle stage, specification completeness, engineering-module implementation status, last run and validation summary, related design file locations, and next action. Distinguish “module not implemented” from “product not evaluated.” Use clear empty states and evidence links.
31. Agent Instructions — Codex (Copy into Task Brief)
Build the Mendex Studio v0.1 engineering core only. Read AGENTS.md, docs/architecture.md and contracts/ before edits. Own src/mendex_core/, tests/core/, schemas/migrations and scripts. 33. Daily Integration and Acceptance Checklist
Day 1: app launches; product persists after restart; specification fields round-trip without loss.
Day 2: plugin registry lists known adapters; absent engineering tools show “not installed”; validation can record “not evaluated”; UI shows real persisted data.
Day 3: product created → revision saved → workspace folders created → project opened in VS Code → tool diagnostic performed → manual evidence attached → report exported with correct status and provenance.
Regression: tests run without external simulators; no PASS without evidence; missing binaries handled; invalid paths rejected; report contains revision ID and warnings.
Release: installation steps reproduced, branch integration complete, known limitations documented, v0.1.0 tag created, demo recorded or screenshots captured.
34. Post-Foundation Enhancement Policy
Enhance only against real product needs. Priority backlog: (1) transformer analytical calculator with benchmark tests; (2) LTspice reference simulation runner with actual logs and parsing; (3) FEMM magnetic model automation with independently checked reference case; (4) KiCad ERC/DRC import; (5) power-device switching-loss analysis; (6) evidence-rich PDF/Word reports; (7) revision diff and design impact; (8) optional AI read-only assistant. Every enhancement needs a requirement, contract change review, automated test, example evidence, UI status and release note.
Safety: simulation does not establish compliance, isolation integrity or suitability for high-voltage hardware. High-voltage prototypes require qualified review, physical testing, documented safety procedures and separate manufacturing approval. No automatic release gate may be bypassed by AI.
